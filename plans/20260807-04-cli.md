# Command-line table stakes

Roadmap 0.4: `--version`, a `--help` worth printing, a way to list ALSA
devices, and startup errors that name the actual problem. The bar is a
stranger on a Pi getting from "installed it" to "it plays" without reading the
source.

## Background

What the binaries do today:

- **No `--version`** in either binary. The first thing a bug report needs is
  the one thing the binary cannot say.
- **`--help` is a punishment**: both binaries print a single usage line to
  *stderr* and exit *2* — asking for help is treated as an error, and the line
  names the flags without saying what any of them do or default to.
- **A wrong `--alsa-device` is silent.** Worse than the roadmap's "fails at
  stream start": `AlsaSink::open` logs one `warn!` and continues **decode-only**
  ([player.rs](../openairplay2-receiver/src/player.rs)) — the iPhone shows
  music playing, the room is silent, and the only clue is one log line
  mid-session on a box the user probably isn't watching. This is the #1
  first-run failure on a Pi, and today it does not even *fail*.
- **Port and Avahi errors are already decent** — the library wraps the bind
  error as `cannot bind control port {port}: …`
  ([receiver.rs](../openairplay2/src/receiver.rs)) and the Avahi warning
  already asks "is avahi-daemon running?". These need at most a nudge, not a
  redesign.

## Scope

Both binaries get `--version` and a real `--help`. The receiver additionally
gets `--list-devices` and a startup probe of the ALSA device. No library
changes: everything here is binary-side, and the bind/Avahi messages the
library already produces are good.

**Out of scope:**

- A `clap`-style dependency. The hand-rolled parsers stay — two small binaries
  with a handful of flags each do not need an argument-parsing framework; they
  need the parsers they have to be testable and the output to be helpful.
- Environment-variable configuration — that is the `/etc/default` roadmap item,
  which will build on this parser (sequencing note below).
- The tui's *runtime* error reporting (connect failures, terminal detection);
  it has its own log-file story. Only its `--help`/`--version` change here.
- Library API changes of any kind.

## Design

### Parser shape (both binaries)

`parse_args` currently reads `std::env::args` directly and `exit(2)`s from
inside the parser, which is why it has no tests. Refactor to:

```rust
enum Action { Run(Args), Help, Version, ListDevices /* receiver only */ }
fn parse(args: impl Iterator<Item = String>) -> Result<Action, String>
```

`main` matches: `Help` prints the help text to **stdout** and exits **0**;
`Version` prints `openairplay2-receiver {CARGO_PKG_VERSION}` (stdout, 0);
`Err(msg)` prints the message and the usage line to stderr and exits 2 —
unchanged for actual mistakes. The parser itself never touches the process or
the environment, so it gets unit tests.

### Help text

A `HELP` constant per binary: usage line, then one line per flag with its
value shape, what it does, and its default — roughly the shape of the options
table already in the README, condensed. Help goes to stdout because piping
`--help` into a pager is the normal thing to do.

### `--list-devices` (receiver)

The `alsa` crate's `HintIter` — the same enumeration `aplay -L` does — printed
as one device name per line with its description indented beneath, playback
devices only, exit 0. This is the answer printed by the probe's failure hint,
so a user never has to leave the binary to find the right name.

### The ALSA startup probe (receiver)

With audio enabled, `main` opens the configured device once at startup (open,
then immediately drop) before the receiver starts, and triages the failure by
`errno`:

- **Not found** → hard error, exit 1: name the device, say it does not exist,
  point at `--list-devices`. A typo should fail in the user's face, not in a
  log they aren't reading.
- **Permission denied** → hard error, exit 1, with the actual fix: the user is
  not in the `audio` group. (The packaged service is; a hand-run binary often
  is not.)
- **Busy** → `warn!` and continue: another program is holding the device *now*,
  which says nothing about stream time. Refusing to start would make the
  receiver unable to coexist with anything.
- Anything else → `warn!` and continue, conservatively.

`AlsaSink::open`'s warn-and-decode-only behavior stays as the mid-session
fallback — after a successful probe it is the rare case (device unplugged
since startup), not the common one (typo), and killing a live session over it
would be worse.

### Message polish

- The binary's final `server error: {e}` line becomes `error: {e}` with, for
  the `AddrInUse` case, the one question worth asking appended: another
  receiver already running on this port?
- Avahi: no change; the existing warning already names the daemon.

### Sequencing

This lands before the `/etc/default` configuration item, which will extend the
same parser with environment-variable fallbacks — `Action`/`parse` is the
shape that item builds on, so it rebases on this rather than colliding with
it.

## Test strategy

- **Parser unit tests, both binaries** (the refactor's point): every flag
  parses; `--help`/`--version`/`--list-devices` yield their `Action`s; a flag
  missing its value, a malformed `--mac`/`--port`, and an unknown argument
  yield `Err`; defaults come out right; later flags override earlier ones
  (`--alsa-device X --no-audio`).
- **Help-text drift test**: every flag string the parser accepts appears in
  `HELP`. Cheap, and it makes "added a flag, forgot the help" impossible.
- **The probe's triage** is a match on `alsa::Error` errno values; test the
  triage function directly with constructed errors. The probe end-to-end and
  `--list-devices` output are hardware checks (below) — CI containers have no
  sound devices worth asserting about.
- **Hardware (skynet)**: `--version` and `--help` look right in both binaries;
  `--list-devices` lists the real devices; `--alsa-device nonsense` exits 1
  naming the device and the fix; `--alsa-device <real>` still plays from a
  real sender; a second receiver on the same port says so plainly.

## Acceptance criteria

- `openairplay2-receiver --version` and `openairplay2-tui --version` print
  name and version, exit 0.
- `--help` on both prints a description of every flag with its default, to
  stdout, exit 0; usage errors still go to stderr with exit 2.
- `openairplay2-receiver --list-devices` prints the playback devices with
  descriptions.
- A nonexistent `--alsa-device` is a startup **error** that names the device
  and points at `--list-devices` — the silent decode-only start is gone for
  the typo case. Permission-denied names the `audio` group. Busy warns and
  starts.
- Parser and help-drift tests run in CI for both binaries.
- README option tables match the new reality (they already describe flags;
  verify nothing drifts).
