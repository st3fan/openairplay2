# Persistent pairing ("pincode") for the AirPlay 2 receiver

- **Date:** 2026-08-05 (revised from "configurable pairing PIN" after hardware
  testing disproved the transient-PIN approach)
- **Status:** proposed
- **Scope:** this repository only. The AirPlay 2 analog of
  [openairplay1](../../openairplay1)-style `--password` protection. Its
  interface is kept as close to openairplay1's as the protocol allows.
  **This plan revises `20260805-01`** — the earlier "make the transient
  pairing PIN configurable" approach was tested against a real iPhone and
  cannot work; this document replaces it.

## Background: why the first attempt failed

AirPlay 2 has no AirPlay 1-style Digest password. Its access control is
*pairing*, and pairing comes in two flavours (confirmed by shairport-sync's
`pair_ap` pairing library and by a live test against an iPhone on iOS 26):

- **Transient pairing** — "no code from the user"; the client does a two-step
  `/pair-setup` (M1→M4) with a **fixed code `3939`**. This is what openairplay2
  implements today, and what every connection has used so far.
- **Persistent (normal) pairing** — the client needs a **one-time setup code**
  typed by the user; it does the full `/pair-setup` (M1→**M6**, the last
  round exchanging Ed25519 identities), stores the pairing, and **henceforth
  authenticates with `/pair-verify`**.

The first plan threaded a configurable PIN into *transient* pairing. The live
test (iPhone, iOS 26, `--password 4321`) proved that cannot work: the iPhone
sent the `transient=true` M1 and an M3 proof derived from the **fixed `3939`**,
SRP verification failed, and iOS gave up with "Unable to connect". Transient
pairing is by design code-less, so a user-entered value has nowhere to go on
the wire. That approach is dead; **the "pincode" is the setup code of
persistent pairing**, and the real feature is persistent pairing itself
(currently listed as unimplemented in `CLAUDE.md`: "pair-verify / persistent
(non-transient) pairing").

## Goals

- Interface parity with openairplay1: `Config.password: Option<String>` /
  `ReceiverBuilder::password(..)` / receiver `--password CODE`, where the
  value is the **persistent-pairing setup code** (a sender must enter it once
  to pair; the default is `3939` so existing behavior is unchanged).
- Implement persistent `/pair-setup` (M1→M6, including the encrypted Ed25519
  identity exchange) and `/pair-verify` (M1→M4).
- Persist paired controllers so a pairing survives a restart.
- **Gate streaming on pairing**: when a password is set, a sender that has not
  completed persistent pairing (or `pair-verify` against a stored controller)
  cannot stream. Transient pairing is refused for a protected receiver; with
  no password set, behavior stays exactly as today (transient, `3939`).
- The setup code never appears in logs, responses, or the advertisement.
- Library stays ALSA-free and macOS-green.

## Non-goals

- Any audio or playback change; no PTP/multi-room.
- Admin removal of pairings (a dev-time / file-delete path is fine; no UI).
- FairPlay changes.
- Making the receiver a HomeKit *accessory* in the Home app (that's a wider
  pairing/`_hap._tcp` ecosystem beyond AirPlay 2 audio; out of scope).
- Forcing persistent pairing when no password is configured (drop-in default).

## Background: the pairing protocol (HAP "Pairing" sub-spec)

Persistent pairing is the HomeKit Accessory Protocol *Pairing* flow with the
SRP group already in use. openairplay2 has every crypto primitive except one:

- SRP-6a M1→M4 — **already implemented** (`srp.rs`, 3072-bit group). Persistent
  setup reuses M1→M4 unchanged; the only difference is what follows.
- Ed25519 long-term identities — `ed25519-dalek` (already a dep), used for the
  receiver's own `Identity` and for signing/verifying the identity exchange.
- HKDF-SHA512 key derivation — `hkdf` + `sha2` (already deps).
- ChaCha20-Poly1305 — `chacha20poly1305` (already a dep) for the encrypted
  M5/M6 envelopes and the session channel.
- **X25519 (Curve25519) key agreement** — used by `/pair-verify` for the
  ephemeral key exchange (`crypto_scalarmult` in shairport's port); **not a
  dependency yet**. Add `x25519-dalek`.

### Persistent pair-setup (server side)

1. **M1→M4** — SRP, exactly as today, but for a *non-transient* client the
   session does not end at M4. `K` (the SRP shared secret) is used with HKDF
   to derive the keys for the encrypted identity envelopes, not directly as
   the channel key.
2. **M5** — the client sends `EncryptedData` (HAP pairing envelope: a
   ChaCha20-Poly1305 blob) containing its long-term Ed25519 `PublicKey`, a
   `Signature`, and its `Identifier`. The signature binds the client's
   ephemeral and long-term keys so the server can trust it controls the
   long-term key.
3. **M6** — the server replies with its own encrypted `PublicKey` +
   `Signature` + `Identifier` (its Ed25519 identity, which it already holds).
   After M6 both sides derive the final shared secret from `K` and the two
   long-term keys, HKDF'd to the per-direction channel keys.
4. The server **persists** the controller's `(identifier, publicKey)` (and the
   salt/verifier, needed to re-run SRP on a later pair-setup) so a restart
   keeps the pairing.

### Pair-verify (server side), on later connections

Done over the plaintext channel before any encrypted session state:

1. **M1** — client sends its long-term Ed25519 `PublicKey` and an X25519
   ephemeral public key.
2. **M2** — server looks up the public key in the store; if unknown, refuse.
   It replies with its own long-term key, an X25519 ephemeral, a signature,
   and its identifier. Both sides compute the shared secret from the X25519
   ephemerals and the long-term keys (HKDF), then sign to prove key control.
3. **M3 / M4** — proof exchange; after M4 the derived secret becomes the
   session channel key, exactly where transient pairing's `K` was used before.

## Design

### Config / interface (parity with openairplay1)

- `Config.password: Option<String>` — the persistent-pairing setup code,
  used as the SRP password for non-transient client-initiated pairing.
  `None` → the default `3939` (and, to preserve drop-in behavior, keep the
  receiver otherwise behaving as it does today). Never logged.
- `ReceiverBuilder::password(..)`; receiver `--password CODE`. (Already
  threaded from the previous revision; semantics change from "transient pin"
  to "persistent setup code".)
- Drop-in guarantee: with no `--password`, transient pairing + `3939`
  continues to work exactly as today.

### Modules

- **`pairing.rs`** — extend `PairSetup` to a full non-transient state machine:
  after M4 (non-transient), accept state 5 (decrypt the client's identity
  envelope, verify its signature, store the controller) and produce state 6
  (our identity envelope). Add `Outcome::Paired { shared_secret }` distinct
  from the transient `Done`. Refuse transient pairing when the receiver is
  protected (`config.password.is_some()`).
- **New `pair_verify`** (server context, in `pairing.rs` or a new module):
  the M1→M4 state machine above, ending in `Outcome::Verified {
  shared_secret }` used to install the channel cipher.
- **New `store`** — a durable paired-controller registry
  `(identifier, public_key, salt, verifier)`. Persisted to a configurable
  path (default `~/.config/openairplay2/pairings`, alongside
  `~/.config/openairplay2/identity`), load/save at receiver start, atomic
  write. Lookup by public key (and identifier) for `pair-verify`. A dev-only
  "clear" path (delete the file) is the MVP admin surface.
- **`server.rs`** — route `/pair-verify` (currently `501`); pass the store
  and the configured setup code into the pairing contexts; refuse transient
  setup when protected; gate the session.
- **`crypto`** — the HAP identity-envelope encryption/signing and the
  X25519/HKDF pair-verify key derivation as testable pure functions.

### Advertising — the open hardware question

`pair-verify` only exists if the sender chooses persistent pairing, and iOS
chooses based partly on the receiver's advertised capabilities and whether it
already has a stored pairing. The `features`/`status` bits that signal a
code-requiring (non-transient) speaker — and whether a fresh identity makes
iOS prompt for the setup code on first contact — are **pinned against a real
device in Phase 1**, like the metadata feature-bits were. Until then the
design keeps `config.password` the only knob; advertising is adjusted to the
evidence.

## Phases

A stack on top of the (revised) plan, per [CLAUDE.md](CLAUDE.md). Phase 2 is a
**verification/test phase** again, exactly as the AirPlay 1 password work did:
no production protocol code is written against an unverified wire format until
the real exchange is pinned. The artifact of Phase 2 is the **start of
`notes/protocol.md`**.

1. **Groundwork (no wire assumptions)** — add `x25519-dalek`; the
   pair-verify X25519 + HKDF shared-secret primitive; the paired-controller
   store (persist/load, lookup by public key, atomic write). All unambiguous
   and unit-tested locally; nothing here is hostage to the exact wire framing.
2. **Verification/test — pin the wire, start `notes/protocol.md`** — probe a
   real sender against a receiver that advertises a code-requiring (persistent)
   receiver with `RUST_LOG=debug`, and capture what iOS actually sends: the
   M1→M6 `pair-setup` framing (including the M5/M6 encrypted identity
   envelope's salt/info strings and key derivation), the M1→M4 `pair-verify`
   request/response bytes, whether iOS prompts for the setup code on a fresh
   identity, and which `features`/`status` bits make it choose persistent
   pairing. **Write the findings into a new `notes/protocol.md`** (the AirPlay 2
   password/pairing protocol record), which becomes the test vectors and the
   reference for phases 3–4.
3. **Persistent pair-setup (M5/M6)** — implement states 5/6 against the
   Phase-2 evidence: decrypt and verify the client's identity envelope, emit
   our own, persist the controller, emit `Paired`. Unit test with a synthetic
   client.
4. **Pair-verify + the gate** — the `pair-verify` state machine, routing in
   `server.rs`, and the gate: protected receiver refuses transient pairing and
   requires `Verified` (or a completed `Paired` this session) before stream.
   Integration test with a synthetic verify client; hardware check that a
   previously-paired sender streams without re-prompting and an unpaired one
   cannot.
5. **Config/CLI + docs** — the `--password` semantics already exist from the
   previous revision; this phase corrects their meaning (setup code), updates
   README/CLAUDE and the runbook for clearing the store.

## Test strategy

- Unit: identity-envelope encrypt/decrypt round-trip + wrong-key failure;
  signature verify (accept/reject); X25519/HKDF pair-verify key derivation
  (two sides agree, differ with swapped keys, wrong store entry); store
  round-trip + atomic-write + lookup-miss; `PairSetup` M5/M6 with a synthetic
  controller.
- Integration (through the `#[doc(hidden)]` test sender): a synthetic client
  completes persistent M1→M6 and gets `Paired`; a second connection completes
  `pair-verify` and reaches the encrypted channel; an unpaired client's
  `pair-verify` is refused; a protected receiver rejects transient setup.
- Hardware (per phase, real Mac/iPhone): the existing tests recall, plus
  (P2) fresh identity → does iOS prompt and accept `--password`? and
  (P4) re-pair after restart; unpaired device refused; wrong code refused.
- **The Phase-2 verification record lives in `notes/protocol.md`** — the
  captured M5/M6 and `pair-verify` framing, the iOS prompt behaviour, and the
  feature bits, kept as the protocol reference and test vectors (the AirPlay
  2 counterpart of openairplay1's `notes/protocol.md`).

## Acceptance criteria

- `cargo build --release && cargo test && cargo clippy --all-targets &&
  cargo fmt --check` green; library ALSA-free and macOS-green; new dep only
  `x25519-dalek` (pure, portable).
- No `--password`: behavior identical to today (transient, `3939`); existing
  tests unmodified and green.
- With `--password`, a real sender: (a) with a fresh identity, is prompted for
  and accepts the code and streams; (b) after a receiver restart, streams via
  `pair-verify` without re-prompting; (c) an unpaired sender cannot stream;
  (d) the wrong code is refused.
- Pairings persist across restarts; clearing the store file removes them.
- The setup code appears nowhere in logs, responses, or the advertisement.
- `--password` documented; `Config.password` documents the AirPlay 2 semantic
  (persistent-pairing setup code; unset = transient `3939`, not open).

## Risks / open questions

- **Does iOS prompt for the setup code on first contact with a software
  receiver?** Phase 2 settles it with a fresh identity; if iOS refuses to
  offer persistent pairing unless certain feature bits are set, advertising
  changes follow the evidence (mirroring the metadata feature-bits fix).
- **Storage security/format** — plaintext peer keys on disk (like `identity`);
  acceptable for this project, documented.
- **Scope** — this is a genuine milestone (the `pair-verify` gap is the last
  listed unimplemented item in `CLAUDE.md`); expect hardware iteration.

## Follow-ups (not in this plan)

- `pair-remove`/safe-evict admin interface beyond deleting the store file.
- HomeKit Home-app accessory integration (`_hap._tcp`).
