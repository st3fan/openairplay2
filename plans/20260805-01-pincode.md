# Pincode protection for the AirPlay 2 receiver

- **Date:** 2026-08-05
- **Status:** validated on hardware; proposed for the stack
- **Scope:** this repository only. The AirPlay 2 analog of
  [openairplay1](../../openairplay1)-style `--password` protection, adapted to
  how AirPlay 2 actually gates access. Kept minimal and focused on what a real
  sender exercises.

## Background

AirPlay 2 has no AirPlay 1-style Digest password (openairplay1's mechanism);
its access control is **pairing**, and the receiver's `--pincode` is a shared
secret a sender must enter to pair. The user asked for a pincode whose default
behaviour is open (transient) so a trusted home network still just works:

- **No `--pincode`** → the receiver advertises nothing special and pairs
  transiently with the standard `3939` (unchanged, drop-in).
- **`--pincode CODE`** → the receiver advertises "password required" and a
  sender must enter `CODE` to pair; only then does a session start.

## The mechanism (pinned on hardware, iOS 26)

Verified against a real iPhone. When a pincode is configured:

1. The receiver sets AirPlay status-flag **bit 7** ("Password required"),
   which is what makes Apple senders choose pairing-with-a-code over
   transient (`0x4` → `0x84`; read from `GET /info` `statusFlags` and the
   `flags=` TXT). **Without this bit, iOS silently uses transient `3939`.**
2. A sender that sees it sends **`POST /pair-pin-start`**; the receiver answers
   an **empty 200** ("the device displays the code" — for a headless receiver
   the code is our `--pincode`, which the user types on the sender).
3. The sender then does `pair-setup` **M1–M4 (SRP)** using the entered code as
   the SRP password. The receiver verifies it: the wrong code fails SRP proof
   verification; the right one passes.
4. On M4 the receiver installs the **encrypted channel** with the SRP session
   key `K` — exactly the existing transient path — and iOS proceeds to an
   encrypted `SETUP`, transport, and audio.

Notable findings (recorded in `notes/protocol.md`):
- The `0x10` "transient" flag in the SRP `pair-setup` **is not** the
  pincode-vs-transient discriminator — iOS sets it in both cases. The
  discriminator is the status bit 7 lede + `pair-pin-start`.
- **iOS does not send M5/M6** in this flow: it completes at M4 + encrypted
  channel. So the HomeKit identity exchange and `pair-verify` are not
  exercised and are **out of scope here** (follow-up, below). `pair-verify`
  would add durable controller storage for "a remembered device streams
  without re-entering the code" — iOS already remembers the code sender-side,
  so it isn't needed for the gate.

## Interface (parity with openairplay1)

Same shape as openairplay1's `Config.password`:
`Config.pincode: Option<String>`, `ReceiverBuilder::pincode(..)`, receiver
`--pincode CODE`. In openairplay2 `None` means "transient `3939`" (not an
open/no-auth mode) because AirPlay 2 always pairs; documented on the field.
The pincode is never logged.

## Scope

In:
- `Config.pincode` + `ReceiverBuilder::pincode` + `--pincode` CLI flag.
- Status-flag bit 7 set when a pincode is configured.
- `/pair-pin-start` answered with an empty 200.
- `pair-setup` SRP password = the configured pincode (else `3939`).
- Unit + integration tests; README/CLAUDE/`notes/protocol.md`.

Out of scope (follow-up, separate plan): `pair-verify`, durable paired-
controller storage, the HomeKit M5/M6 identity exchange, and any admin
"forget this device" surface. (Exploratory groundwork for those — an X25519
primitive, a controller store, and an M5/M6 implementation — was built and
then removed from this stack because hardware showed iOS does not exercise
them in the pincode flow; recording here so they are not lost.)

## Phases

1. **Implementation** — the minimal surface above, with tests: `--pincode`
   sets bit 7 and becomes the SRP password; `pair-pin-start` → 200; correct
   code pairs and streams, wrong code fails SRP; no pincode stays transient
   `3939` (drop-in). Receiver CLI + README/CLAUDE.
2. **Protocol record** — `notes/protocol.md`: the AirPlay 2 pairing/pincode
   wire behaviour captured on iOS 26 (bit 7, `pair-pin-start`, the 0x10-flag
   caveat, M4 + encrypted channel, the free-text "password" dialog).

## Acceptance criteria

- `cargo build --release && cargo test && cargo clippy --all-targets &&
  cargo fmt --check` green; library ALSA-free and macOS-green; transient
  default and all existing tests unchanged.
- **Hardware (iOS 26, done):** with `--pincode`, the phone prompts; wrong code
  is refused at SRP; the right code pairs and streams audio. Without
  `--pincode`, a sender streams transiently as before.
- The pincode appears nowhere in logs, responses, or the advertisement
  (only the boolean bit 7 is advertised).
- `--pincode` documented in the README/usage; CLAUDE.md reflects the feature.
