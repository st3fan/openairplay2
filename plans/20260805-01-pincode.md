# Configurable pairing PIN (pincode) for the AirPlay 2 receiver

- **Date:** 2026-08-05
- **Status:** proposed
- **Scope:** this repository only. The AirPlay 2 analog of
  [openairplay1](../../openairplay1)-style `--password` protection. The
  protocol differs from AirPlay 1 (it has no RFC 2617 Digest auth), so the
  *mechanism* is openairplay2's pairing PIN, but the *Rust interface* is kept
  as close to openairplay1's as possible.

## Background

openairplay1 gained an optional password (`Config.password` /
`ReceiverBuilder::password` / `--password CODE`): AirPlay 1, gated at the
RTSP level with RFC 2617 Digest auth. AirPlay 2 has **no such mechanism** —
its access control is pairing. A would-be sender must complete transient
`pair-setup` (SRP-6a, M1→M4) before the channel is encrypted and any stream
is accepted, and that exchange authenticates with a PIN that is currently a
hardcoded constant, `PAIR_SETUP_PIN = "3939"`
([pairing.rs](../openairplay2/src/pairing.rs)). Anyone on the LAN can stream
because everyone knows the fixed code.

The user wants a "pincode" for openairplay2, manually testable exactly like
the AirPlay 1 one (set a value, type it into the sender when it connects).
The natural AirPlay 2 mechanism is exactly the pairing PIN: make it
configurable, and a sender that doesn't know the room's PIN cannot complete
pairing and cannot stream. The default stays `3939`, so nothing changes for
existing setups that don't set one.

## Goals

- Interface parity with openairplay1: the same `Config.password:
  Option<String>`, `ReceiverBuilder::password(..)`, and receiver
  `--password CODE` flag.
- When a password is set, a sender must enter it to pair; the wrong value
  fails SRP authentication and no stream starts.
- When unset, behavior is byte-for-byte identical to today (default PIN
  `3939`).
- The PIN never appears in logs, responses, or the advertisement.
- Library still ALSA-free and macOS-green; no new dependencies.

## Interface parity — the one semantic difference

openairplay1's `Config.password: Option<String>` has `None` = **no
authentication at all** (the receiver is open). AirPlay 2 has no pairless
mode — every connection must pair — so `None` cannot mean "open". In
openairplay2 `None` means the **historical default PIN `3939`**, and
`Some(pin)` means the room's PIN is `pin`. The Rust shape is identical to
openairplay1's (same field, same builder method, same `--password` flag);
only the meaning of the unset default differs, and AirPlay 2's always-pair
model makes that unavoidable. This is documented on the field so embedders
moving between the two receivers are not surprised.

## Non-goals

- **Persistent `pair-verify` pairing** ("only devices that have previously
  paired may stream") — that is the stronger access-control model, but it is
  a substantially larger feature: M5/M6 Ed25519 identity exchange, durable
  storage of peer keys, and the `pair-verify` protocol, all currently
  unimplemented. It does not involve the user typing a PIN each time, so it
  is not what the manual test exercises. Recorded as a follow-up; not part
  of this plan.
- Any pairing-PIN display UI on the receiver side.
- Changing the SRP/HomeKit exchange, the `features` bitmask, or the TXT
  records — senders prompt for the PIN during `pair-setup` regardless of
  advertising (the existing hardware passes confirm the flow), so nothing to
  advertise.

## Design

- `Config` gains `pub password: Option<String>`: "a sender must present this
  in transient pair-setup to stream; `None` → the historical default PIN
  `3939` (AirPlay 2 always requires pairing — this is not an 'open' mode)."
- `ReceiverBuilder::password(impl Into<String>)`; `build()` stores it in
  `Config`.
- `PairSetup::new(pin)` (replaces the `Default` impl); it stores the pin and
  `handle_m1` calls `SrpServer::new(pin)` in place of the `PAIR_SETUP_PIN`
  constant. The constant becomes the default value used by the server.
- `server.rs::handle_connection`: `let pin =
  context.config.password.as_deref().unwrap_or(PAIR_SETUP_PIN); let mut pair
  = PairSetup::new(pin);` — the only wiring change in the server.
- Receiver CLI (`openairplay2-receiver`): `--password CODE` argument +
  parse + `builder.password(..)`, and a startup `info!` line that names the
  state without printing the value (e.g. "pairing PIN: configured").
- The PIN is typically numeric (AirPlay senders present a numeric entry UI,
  and the default `3939` is numeric), but the SRP password is a string, so
  any value works on the wire; the manual test uses a numeric code.

## Phases

Single implementation phase — the change is contained (one config field, one
builder method, one `PairSetup` constructor + one server call site, one CLI
flag, tests).

## Test strategy

- **pairing.rs unit tests** (the change's core): `PairSetup::new("1234")`
  completes transient pairing against an `SrpClient::new("1234")` (success),
  and pairing with `SrpClient::new("0000")` fails SRP authentication
  (refused). Uses the existing test-side `SrpClient` harness in
  [srp.rs](../openairplay2/src/srp.rs).
- **Default path**: `PairSetup::new(PAIR_SETUP_PIN)` behaves exactly as
  today; existing pairing tests are untouched and green.
- **Receiver**: `--password` parse and `ReceiverBuilder::password` round-trip
  (mirror the openairplay1 tests).
- **Hardware (acceptance)**: set `--password`, connect a real sender — the
  wrong code is refused (no stream), the right code pairs and streams, and
  `RUST_LOG=debug` over the interaction contains no trace of the PIN
  (verified manually like the AirPlay 1 test).

## Acceptance criteria

- `cargo build --release && cargo test && cargo clippy --all-targets &&
  cargo fmt --check` green; library ALSA-free and macOS-green
  (`cargo test -p openairplay2`), no new dependency.
- Without `--password`, behavior is identical to today (default PIN `3939`,
  existing tests unmodified and green).
- With `--password`, a sender that doesn't know it cannot pair/stream; the
  right one can. The refusal is the existing SRP authentication failure —
  no `SessionStarted`.
- The PIN appears nowhere in logs, responses, or the advertisement.
- `--password` documented in the receiver usage string and README; `Config`
  documents the AirPlay 2 semantic (unset = default PIN, not open).

## Follow-ups (out of scope here)
