# Configure everything from /etc/default/openairplay2-receiver

Roadmap 0.4: every receiver option gets its own named environment variable —
including the now-playing endpoint's enable, address and **password** — read
by the binary itself, with a command-line flag still winning. The opaque
`OPENAIRPLAY2_ARGS` blob is removed, and the upgrade announces itself.

## Background

Today `/etc/default/openairplay2-receiver` holds one variable,
`OPENAIRPLAY2_ARGS`, which the systemd unit splices onto the command line.
That has two real problems, both admitted in the unit file's own comments:

- **The pincode leaks.** Options travel on the command line, and
  `/proc/<pid>/cmdline` is world-readable — any local user reads the pincode
  out of `ps`. The conffile's root-only 0640 protects the file and nothing
  else. `/proc/<pid>/environ` is readable only by the process's own user and
  root, so environment variables actually close this hole.
- **The file is a shell blob, not configuration.** One long quoted string of
  flags, with quoting rules nobody remembers, no way to comment out a single
  option, and nothing the daemon can validate or name in an error.

Separately, the now-playing WebSocket has **no authentication of any kind**:
anyone who can reach the port gets track metadata and cover art, and the only
mitigation is a comment suggesting loopback. Its password is part of this
plan because the options file is where that password has to live — a
password feature without a safe place to put the password would be decoration.

Decisions already taken (roadmap PR #72 discussion): named variables replace
the blob; the flag wins over the variable; `OPENAIRPLAY2_ARGS` is **removed
rather than kept alongside** — a preserved conffile silently half-working is
worse than a loud break — so the upgrade must announce itself; the endpoint
gets a shared secret compared in constant time before the WebSocket upgrade.

This plan builds directly on the `parse(args) → Result<Action, String>` shape
from the CLI plan ([20260807-04](20260807-04-cli.md), stack #81): the
implementation phases rebase onto that stack once it merges.

## Scope

Two implementation phases on this plan's stack.

**Phase 1 — the configuration mechanism, and the migration:**

- An environment variable per receiver option, `OPENAIRPLAY2_`-prefixed.
- Precedence: command-line flag > environment variable > built-in default.
- `%h` (hostname) substitution in the name, whichever way the name arrives.
- `OPENAIRPLAY2_ARGS` removed from the unit and the options file; the daemon
  logs an **error** naming the migration when it finds the variable set; the
  package announces the change at upgrade time.

**Phase 2 — the endpoint password, end to end:**

- The receiver rejects WebSocket upgrades without the right password when one
  is configured; `openairplay2-tui` learns to send it.

**Out of scope:**

- Environment-variable configuration of the tui beyond the password — the
  display is an interactive program someone runs by hand, not a service read
  from an options file.
- A config-file format of our own (TOML etc.): `/etc/default` + environment
  variables is the Debian-native mechanism the unit already uses, and one
  mechanism is the point.
- TLS on the endpoint; the threat model is the local network, and the pairing
  channel it mirrors is the sender's concern, not the display's.
- Binding restrictions on the endpoint (refuse non-loopback without a
  password): considered, rejected — the roadmap decision was a password, and
  a refusal would break every existing `--tui-listen 0.0.0.0` setup silently.

## Design

### The variables (phase 1)

| Variable | Flag it mirrors | Value |
| --- | --- | --- |
| `OPENAIRPLAY2_NAME` | `--name` | free text, `%h` → hostname |
| `OPENAIRPLAY2_PORT` | `--port` | 1–65535 |
| `OPENAIRPLAY2_MAC` | `--mac` | `AA:BB:CC:DD:EE:FF` |
| `OPENAIRPLAY2_IDENTITY_FILE` | `--identity-file` | path |
| `OPENAIRPLAY2_PINCODE` | `--pincode` | the code |
| `OPENAIRPLAY2_AVAHI` | `--no-avahi` | `on` / `off` (default `on`) |
| `OPENAIRPLAY2_AUDIO` | `--no-audio` | `on` / `off` (default `on`) |
| `OPENAIRPLAY2_ALSA_DEVICE` | `--alsa-device` | device name |
| `OPENAIRPLAY2_TUI_LISTEN` | `--tui-listen` | listen address |
| `OPENAIRPLAY2_TUI_PASSWORD` | `--tui-password` (new) | the password |

Booleans are exactly `on` or `off` — anything else is a startup error naming
the variable and the value, in keeping with "fail loudly". An **empty**
variable is *unset*, not an error: an options file line edited to
`OPENAIRPLAY2_NAME=` means "default", which is what the person editing meant.

### Resolution (phase 1)

`parse()` stays pure over `argv` and untouched. A new pure step merges the
environment in behind it:

```rust
fn resolve(args: Args, env: impl Fn(&str) -> Option<String>) -> Result<Args, String>
```

— fills only the fields the command line left unset, validating each value
with the *same* validators the flags use, so `OPENAIRPLAY2_PORT=x` fails
exactly like `--port x` but names the variable. `Args` grows the tri-state it
needs where a bool hides two flags today (`--alsa-device`/`--no-audio`). The
env lookup is a closure, not `std::env`, for the same reason `parse` takes an
iterator: tests. (`images::multiplexer(env)` in the tui is the in-repo
precedent.)

`%h` substitution happens after resolution, in a pure
`fn substitute(name: &str, hostname: &str) -> String`; `%%` escapes a literal
percent. The hostname comes from `libc::gethostname` at the call site.

The `OPENAIRPLAY2_ARGS` tripwire is part of resolution: if the variable is
set (and non-empty), log at **error** level that it is ignored and how to
migrate, then continue with what is configured — a receiver with a default
name still plays; a refused start plays nothing. This is the daemon-side half
of the upgrade announcement.

### Packaging (phase 1)

- **The options file** (`packaging/openairplay2-receiver.default`) is
  rewritten: one commented-out example line per variable with its default and
  a one-line description, `RUST_LOG` kept. It remains a conffile, root-owned
  0640 — it can hold two secrets now.
- **The unit** drops `$OPENAIRPLAY2_ARGS` from `ExecStart`
  (`--identity-file` stays, for the reasons already commented there), and its
  "does not hide a --pincode" comment inverts: secrets belong in the options
  file precisely *because* they travel by environment now.
- **The upgrade announces itself three ways**: a `NEWS.Debian` entry (the
  Debian-native mechanism, shipped gzipped under
  `/usr/share/doc/openairplay2-receiver/`); the `postinst` greps the
  *preserved* conffile for `^OPENAIRPLAY2_ARGS` and prints a migration notice
  into the apt output people actually see; and the daemon's error log (above)
  for anyone who missed both. dpkg keeps a locally-modified conffile on
  upgrade, so every 0.3/0.4-configured box hits exactly this path.

### The endpoint password (phase 2)

- **Receiver**: when a password is configured, the accept path switches to
  `tokio_tungstenite::accept_hdr_async` and requires
  `Authorization: Bearer <password>` before the upgrade; wrong or missing →
  the handshake is rejected with 401 and a `warn!` naming the peer. The
  comparison is constant-time (byte-fold over max-length, no early exit) —
  not because a LAN timing oracle is likely, but because it costs nothing.
  No password configured → today's `accept_async`, unchanged.
- **Display**: `openairplay2-tui` gains `--password` and reads
  `OPENAIRPLAY2_TUI_PASSWORD` (same precedence rule), building its connect
  request with the header. A 401 is surfaced in the status line as "password
  required" / "wrong password" rather than looking like a dead receiver —
  the retry loop must not hammer a receiver that said no; on 401 it waits the
  long retry interval.
- **No wire-format change**: the password is an HTTP header on the handshake,
  so `openairplay2-tui-protocol` is untouched — deliberately, since that
  crate is now published.
- The README's "keep it on loopback" advice stands; the password is for when
  loopback is not enough.

### Docs

- README: the install section's "same flags as below" becomes the variable
  table; the options table gains a variable column (receiver only); the
  pincode row's `ps` caveat inverts into "use the environment variable".
- The runbook's upgrade verification gains the migration check.

## Test strategy

- **`resolve` unit tests**: each variable fills its field; the flag wins over
  the variable; empty = unset; bad values name the variable; `on`/`off`
  strictness; the `OPENAIRPLAY2_ARGS` tripwire fires only when set and
  non-empty.
- **`substitute` unit tests**: `%h`, `%%`, no-op without `%`.
- **Endpoint auth tests** (the tui.rs WebSocket tests already drive a real
  socket): password set + no header → rejected; wrong password → rejected;
  right password → snapshot arrives; no password configured → header-less
  connect still works (the compatibility case).
- **Constant-time compare**: behavioral tests (equal, unequal, different
  lengths); the timing property is by construction, asserted in a comment,
  not a test.
- **Hardware (skynet)**: install the new `.deb` over a 0.3-style config with
  `OPENAIRPLAY2_ARGS` set → postinst notice in the apt output, error in the
  journal, receiver still up; migrate the file to named variables → name,
  device and pincode all take effect; `tr '\0' '\n' </proc/<pid>/cmdline`
  shows no pincode; the tui connects with the password and is refused
  without it.

## Acceptance criteria

- Every receiver option is settable from
  `/etc/default/openairplay2-receiver` by its own named variable, validated
  with errors that name the variable; a flag on the command line still wins.
- A pincode configured through the file appears in neither
  `/proc/<pid>/cmdline` nor `ps` output.
- `%h` in the name becomes the hostname, so one options file deploys across
  machines unedited.
- An upgraded box with `OPENAIRPLAY2_ARGS` still set gets the postinst
  notice, the NEWS entry, and a journal **error** naming the migration — and
  keeps running.
- With `OPENAIRPLAY2_TUI_PASSWORD` set, a WebSocket client without the
  password gets 401 and no data; `openairplay2-tui --password` (or the
  variable) connects; with no password configured, behavior is unchanged.
- `openairplay2-tui-protocol` is untouched.
