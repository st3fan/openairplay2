# Port the now-playing display: `openairplay2-tui` + `openairplay2-tui-protocol`

- **Date:** 2026-08-05
- **Status:** proposed
- **Scope:** this repository. Port openairplay1's dashboard — the full-screen
  now-playing display with terminal artwork, fed by a WebSocket on the receiver
  — to openairplay2, under the names Stefan chose: **`openairplay2-tui`** and
  **`openairplay2-tui-protocol`**.

## Background

openairplay1 grew a full-screen display of what is currently playing: title,
artist and album centered on screen, cover art rendered as a real image on
terminals that can do it, plus receiver name, sender IP, audio format, volume
and an elapsed/total clock. It started as a `--tui` flag on the receiver and
ended as **its own binary** talking to the receiver over a WebSocket, which is
what made it useful: the receiver runs headless under systemd while a display
comes and goes, possibly from another machine, and several displays can watch
one receiver. The whole design, including the mistakes made on the way, is in
[openairplay1's plan](../../openairplay1/plans/20260803-04-tui.md).

This plan brings that here. The screen does not change and neither does the
seam; what changes is the names (`dashboard` → `tui`, at Stefan's request) and
the three places where AirPlay 2 differs from AirPlay 1.

## What openairplay2 already has, and what it doesn't

| The display needs | openairplay2 today |
|---|---|
| title / artist / album | `Event::Metadata` ✔ |
| cover art | `Event::Artwork` ✔ |
| volume | `Event::Volume { db }` ✔ |
| format (rate, channels) | `Event::SessionStarted { rate, channels }` ✔ |
| session start / end | ✔ |
| **paused** | `Event::Paused(bool)` ✔ — *openairplay1 has no such thing* |
| sender's IP | ✘ — `Session` never sees the peer address |
| elapsed / total | ✘ — no `Event::Progress`, `progress:` line ignored |

So two library gaps, same two openairplay1 had, and one bonus.

### The bonus: pause is real here

AirPlay 1 has no pause on the wire — a pausing iPhone simply stops sending
audio — so openairplay1 could only ever freeze the clock and never say the word
"paused" (its phase 10 remains deliberately unbuilt). AirPlay 2 sends
`SETRATEANCHORTIME` with `rate=0`, which this library already parses and
surfaces as `Event::Paused(bool)`. The display therefore gets an honest
**paused** state, and the protocol carries it.

### The sender's IP

`server::handle_connection` has the peer `SocketAddr`; `Session::new(local_ip,
sink_factory, events)` is never told it. Thread it through and put it where the
"a sender connected" moment already lives:

```rust
SessionStarted {
    rate: u32,
    channels: u8,
    peer: IpAddr,   // new
},
```

`Event` is `#[non_exhaustive]` at the enum level, so new *variants* are
additive, but a new *field* breaks anyone matching
`SessionStarted { rate, channels }` exhaustively. Checked: radiod matches
`Event::SessionStarted { .. }`, so the one embedder in the wild is unaffected;
our own receiver's arm needs updating. It is still a breaking API change on a
published crate — **0.4.0**.

Dual-stack listeners hand out v4-mapped addresses (openairplay1 saw a real
iPhone arrive as `::ffff:192.168.1.42`), so the address is unwrapped for
display.

### Elapsed / total: take the position from the audio, not the sender

openairplay1 learned this the expensive way, and the lesson transfers whole.
The obvious design — extrapolate from the sender's `progress:` reports — is
wrong, because a 24-minute capture showed `progress:` arriving **at track start
and essentially nowhere else** (five stretches of 118–283 s with no report at
all). A display built on it is inventing the clock for minutes at a time, and
the honest-looking fix (stop extrapolating when the report goes stale) freezes
the clock a few seconds into every track.

The receiver knows what the sender never repeats: which RTP timestamp it is
feeding the sink *right now*. Conveniently, openairplay2 is already most of the
way there — `buffered::AudioPacket` parses `timestamp` out of the RTP-ish
header alongside `seq`, and simply drops it. So:

- The player queue, which today stamps each decoded packet with its sequence
  number, also carries the packet's RTP timestamp.
- The playback thread reports position about once a second from the audio it is
  actually playing.
- The track's extent comes from the sender's `progress: <start>/<current>/<end>`
  line in `SET_PARAMETER text/parameters` — which openairplay2 currently parses
  for `volume:` only, ignoring the rest.
- Timestamps are wire concepts and the invariant is that they stay out of the
  public API, so the library divides by the session's sample rate and emits
  durations:

```rust
/// Where playback is, reported about once a second while audio plays.
Progress {
    elapsed: Duration,
    duration: Duration,   // zero when the sender reported no end
},
```

Nothing extrapolates, and **pause needs no special handling in the display**: a
paused sender sends no audio, so reports stop and the last position stands.
`Flushed` must *not* clear the position — a seek is followed by fresh reports,
and clearing makes the clock blink out.

## The seam

Unchanged from openairplay1, which is the point of porting rather than
redesigning: **WebSocket, JSON text frames**, served by the receiver binary,
off unless asked for.

```
openairplay2-receiver --tui-listen 127.0.0.1:7392
openairplay2-tui --connect ws://127.0.0.1:7392
```

Loopback in the example on purpose: the stream carries now-playing metadata and
cover art, which is nobody's business but the user's; binding wider is the
operator's explicit choice. `tokio-tungstenite` over a plain `TcpListener`, as
there.

The endpoint lives in the **receiver binary**, not the library — the library
ends at PCM + events, and radiod (embedder #1) has its own web UI and wants
nothing to do with this.

### Messages

One `#[serde(tag = "type", rename_all = "snake_case")]` enum in
`openairplay2-tui-protocol`, ported from `openairplay1-dashboard-protocol` with
the rename and the pause addition:

```jsonc
// Once, on connect: everything the receiver currently knows.
{"type":"snapshot",
 "receiver":{"name":"Living Room","version":"0.4.0"},
 "session":{"rate":44100,"channels":2,"peer":"192.168.1.42"},   // or null
 "track":{"title":"Sonata No. 1","artist":"…","album":"…"},     // or null
 "volume_db":-12.5,                                              // or null
 "progress":{"elapsed_ms":83000,"duration_ms":247000},           // or null
 "artwork":{"content_type":"image/jpeg","data_base64":"…"},      // or null
 "paused":false}                                                 // new

// Then one message per change.
{"type":"session_started","rate":44100,"channels":2,"peer":"192.168.1.42"}
{"type":"metadata","title":"…","artist":null,"album":"…"}
{"type":"artwork","content_type":"image/jpeg","data_base64":"…"}  // "" = cleared
{"type":"volume","db":-12.5}
{"type":"progress","elapsed_ms":83000,"duration_ms":247000}
{"type":"paused","paused":true}                                   // new
{"type":"flushed"}
{"type":"session_ended"}
```

Durations are integer milliseconds, the peer is a string (v4 or v6), artwork is
base64 so a browser client could use it as a `data:` URL. The delta messages
stay a near-copy of `Event` so the folding code stays trivial.

### Not letting a display hurt the audio path

Both rules come across unchanged, and both are the kind of thing that only
shows up under load:

- The fan-out `broadcast` channel is **bounded**; a client that stops reading is
  dropped from the channel rather than applying backpressure to the event task.
- A client that fell behind is **resynced with a fresh snapshot, not
  disconnected** — artwork frames are hundreds of KB, and a client that missed
  one is better resynced than killed.
- A WebSocket ping on an interval, dropping clients that stop ponging, so a
  laptop that closed its lid doesn't hold a slot forever.

## The display

A near-verbatim port of `openairplay1-dashboard` (~1750 lines across
`tui.rs`, `images.rs`, `client.rs`, `main.rs`): ratatui + crossterm, one
centered column — artwork, title (bold), artist, album, a progress bar and
clock, and a dim status line — with an idle state that shows the receiver name
and "waiting for a sender…", and connection states ("connecting to …",
"connection lost, retrying") reusing that layout. Quit on `q`/`Ctrl-C`;
terminal restored on quit, on error, and **from a panic hook**.

```
┌────────────────────────── 96x30 ───────────────────────────┐
│                    ┌──────────────┐                        │
│                    │   artwork    │                        │
│                    └──────────────┘                        │
│                      Sonata No. 1                          │
│                       Some Artist                          │
│                       Some Album                           │
│                 ━━━━━━━━━━━━━━━━━━━━━━━                    │
│                    1:23 / 4:07  ⏸ paused                   │
│    Living Room · 192.168.1.42 · 44100 Hz 2ch · -12.5 dB    │
└────────────────────────────────────────────────────────────┘
```

The only screen change is the paused indicator next to the clock.

**Artwork** ports unchanged: Kitty graphics for Ghostty/Kitty/WezTerm, iTerm2
inline images for iTerm2/Konsole, text-only elsewhere; JPEG decoded to RGB with
`jpeg-decoder` for Kitty, PNG and iTerm2 passed through untouched; sizing by
cell box so the terminal scales and we never resample; detection by Kitty probe
then environment, forced with `--tui-images=auto|kitty|iterm2|none`; one owned
image id, deleted on track change, on clear, and on exit.

**One nice property of the split:** `openairplay2-tui` depends on neither the
library nor ALSA — it is a WebSocket client and a renderer — so unlike the
receiver it **builds and runs on macOS**. The display can sit on a laptop
watching a Pi. CI's macOS leg gains both new crates, which is what keeps that
true.

## Phases

Each phase is one PR stacked on this plan.

1. **Library: `peer` and `Progress`** — thread the peer address into `Session`
   and onto `SessionStarted`; carry the RTP timestamp through the player queue
   and report `Event::Progress` about once a second from the audio being
   played; parse the `progress:` line in the `text/parameters` path for the
   track extent; `Flushed` stops clearing position. Bump to **0.4.0** and fix
   the receiver's match arm. Unit tests.
2. **Protocol crate and the receiver's endpoint** — `openairplay2-tui-protocol`
   (serde types, no other dependencies) and `--tui-listen ADDR` on the receiver
   with the publisher: snapshot on connect, broadcast fan-out, lag resync,
   ping/timeout. Round-trip and JSON-fixture tests, plus real-socket
   integration tests.
3. **The `openairplay2-tui` binary** — port `tui.rs`, `images.rs`, `client.rs`
   and `main.rs`, add the paused indicator, the reconnect/backoff client and
   connection states. `TestBackend` layout tests, escape-sequence and detection
   tests, all ported. README and CLAUDE.md updated for three binaries.

## Test strategy

- **Ported tests come with the ported code**: `TestBackend` layout assertions
  (idle, playing, missing fields, narrow terminal, too short for artwork),
  exact-bytes tests for both artwork protocols including the delete sequence,
  and capability detection as a pure function over an env map plus probe
  result.
- **New, library side**: `progress:` parsing (malformed, out-of-order,
  `start == end`), timestamp → `Duration` at the session rate, position
  reporting from the player (including the missing-anchor and silence cases),
  `peer` reaching `SessionStarted`, and `Flushed` leaving position alone.
- **New, protocol side**: a fixture test pinning the exact JSON bytes of every
  message — a published wire format that drifts silently is worse than none —
  including `paused` and an empty-artwork clear.
- **New, endpoint side**: real-socket integration tests driven by the existing
  synthetic-sender helpers — the message sequence for a session, a client
  connecting **mid-session** getting track/artwork/progress/paused in its
  snapshot, two clients, and one client that stops reading while the other
  keeps working.
- **Together, in a pty**: receiver and TUI as separate processes (`script` with
  a fixed size), driven by the synthetic sender; kill and restart each in turn
  and watch the other recover.
- **On hardware** (the acceptance gate this project always applies): a real Mac
  streaming to the receiver with the TUI in Ghostty — artwork appears, changes
  per track, clears on `image/none`, survives a resize; pause on the Mac shows
  paused and freezes the clock, resume picks up; a plain `xterm` shows the
  text-only layout with no stray escape bytes; terminal clean on `q`, `Ctrl-C`
  and a forced panic.

## Out of scope

- **Any control of the receiver or the sender from the TUI** — it is read-only:
  no volume, no skip, no pause. (AirPlay 2 does have a remote-control path;
  that is a separate feature.)
- **Authentication or TLS** on the WebSocket (loopback by default; a reverse
  proxy is the answer for anything else), and any browser front end or static
  file serving.
- **Sixel** artwork, mouse input, keyboard interaction beyond quit, a log pane.
- **Publishing `openairplay2-tui` / `openairplay2-tui-protocol` to crates.io**,
  and shipping the TUI binary in the `.deb` — both are natural follow-ups once
  the thing has been used, and both are one-line additions to workflows that
  already exist.
- Any artwork or terminal handling inside the library (it still ends at PCM +
  events), and any change to openairplay1.

## Acceptance criteria

- `openairplay2-tui --connect ws://…` shows title/artist/album centered, plus
  receiver name, sender IP, format, volume and elapsed/total, updating live
  across track changes, with an idle state before and after a session.
- Artwork renders as an image in Ghostty, updates per track, disappears on the
  sender's clear, and re-places after a resize; a terminal without support
  shows the text-only layout with no stray bytes.
- **Pausing on the Mac shows "paused" and freezes the clock; resuming picks up
  where it stopped** — the thing openairplay1 could not honestly do.
- A TUI started mid-track renders the full screen immediately from the
  snapshot, artwork included; either side can be killed and restarted without
  restarting the other; two TUIs stay current; one that stops reading never
  stalls the receiver or the audio.
- Without `--tui-listen` the receiver behaves exactly as today: no listener, no
  extra dependencies in its runtime path.
- The terminal is left clean on `q`, `Ctrl-C`, error exit and panic.
- Library still ALSA-free and macOS-green, and `openairplay2-tui` +
  `openairplay2-tui-protocol` build and test on macOS too (enforced in CI);
  workspace clippy `-D warnings`, fmt and rustdoc clean.
