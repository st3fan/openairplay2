# Testing the `.deb` in a throwaway VM

- **Date:** 2026-08-06
- **Status:** implemented
- **Scope:** a new `testing/vm/` — scripts that boot Debian 13 (trixie, arm64)
  under QEMU on an amd64 host, install a `.deb` into it, and assert that the
  service actually runs. Nothing in the shipped crates changes.

## Background

The `.deb` is the artifact most likely to break silently. Everything about it —
the systemd unit, the `openairplay2` system user, the conffile, the identity in
`/var/lib`, the dependency list — is only exercised when somebody installs it on
a real machine, and `notes/status.md` has said "hardware validation pending" for
the packages since they shipped. The docs audit turned up two package-level
facts nobody had checked: the `.deb` depends on `libasound2t64` and glibc 2.39
without pinning either, and `libc6` is unversioned in `depends`. Those are
exactly the sort of thing an install test catches in thirty seconds and a human
catches after a bad release.

Raspberry Pi OS is the target that matters — it is what the arm64 and armhf
packages exist for — and it is also the one nobody has a spare machine for. It
turned out not to be bootable in a way that helps; see "Host and guest".

## What this is not

Not a replacement for real hardware: emulated aarch64 has no sound card, so
**audio never plays** and pairing with a real sender is out of scope. What the
VM proves is that the package installs cleanly on the real target distribution,
the unit starts, the user and directories are created, and the binary runs far
enough to serve `GET /info`. That is the half that regresses silently.

## Host and guest

- **Host:** Debian 13 amd64 (skynet), and a GitHub runner later. No KVM is
  possible — aarch64 on x86 is TCG emulation, so expect a boot measured in
  minutes, not seconds.
- **Guest:** `debian-13-genericcloud-arm64.qcow2` from `cloud.debian.org`,
  verified against Debian's `SHA512SUMS`.

**Raspberry Pi OS was tried first and abandoned.** Its kernel has no virtio at
all (not built in, not in the initramfs, not in the kernel package), so `-M
virt` cannot find a root disk; and under `-M raspi3b`, where it does boot, the
out-of-tree `dwc_otg` driver NULL-derefs against QEMU's USB model — and a Pi
3B's Ethernet is USB-attached, so no USB means no `apt`. The evidence is in
[`notes/vm-testing.md`](../notes/vm-testing.md). Debian trixie arm64 is the
same distribution release the package is built on and declares its dependencies
against, and the `.deb` is not Pi-specific, so it tests the same things.

**arm64 only, for now.** The VM is aarch64; the cross-compiled armhf package
still has never run anywhere. An armhf guest is a follow-up.

## Booting it

Undramatic, because the cloud image is built for exactly this: UEFI (AAVMF)
boots GRUB, virtio-blk finds the disk, virtio-net gets user-mode networking
with an ssh port forwarded to a free host port.

## Preparing the image without root

No loop mount, no libguestfs, no `sudo` — which is what makes it runnable
unprivileged on a runner:

- the disk is a **qcow2 overlay** on the cached base image, so a run never
  dirties the cache and cleanup is one unlink;
- cloud-init is seeded through a FAT image labelled `CIDATA`, written with
  **mtools** — the NoCloud datasource matches on the *label*, so no ISO tools
  are needed;
- the login is an **ephemeral ed25519 key** generated per run and installed by
  cloud-init, so there is no password anywhere;
- the `.deb` goes in over ssh once the VM is up.

## The test

1. Fetch + verify the base image (cached; ~322 MB, checked against Debian's
   `SHA512SUMS`).
2. Make a qcow2 overlay on it and a cloud-init seed carrying a fresh key.
3. Boot; wait for SSH on the forwarded port, with a timeout that fails loudly.
4. `apt-get install -y ./openairplay2-receiver_*.deb` and assert:
   - the unit is `enabled` and `active`;
   - the `openairplay2` user exists and `/var/lib/openairplay2` belongs to it;
   - `/etc/default/openairplay2-receiver` is a conffile with our text;
   - the identity file appears after start (proof the daemon really ran);
   - `GET /info` on 7000 answers a plist;
   - `journalctl -u` has no fatal errors.
5. Reboot once and re-assert `active` — that is the "starts at boot" claim —
   and insist the avahi advertisement worked, now that avahi is up from the
   start.
6. Remove the package and assert the identity survives, per the runbook's
   upgrade promise.
7. Tear down: power off, delete the work directory.

Every step is an assertion with a message; the script exits non-zero on the
first failure and always tears down.

## Layout

```
testing/vm/
  vmtest               # driver: ./vmtest [--keep] [--release TAG] path/to.deb
  lib/vm.sh            # image fetch/verify, overlay, seed, boot, ssh, teardown
  tests/deb-install.sh # the assertions above
```

Every `tests/*.sh` runs against the booted VM with `ssh_vm`, `scp_vm`,
`assert`, `reboot_vm` and friends in scope, so adding a test is adding a file.
`--release TAG` tests a published artifact instead of a local build.

## CI

Once it is reliable locally, a manually-triggered workflow
(`workflow_dispatch`, plus the release path later) runs the same scripts on
`ubuntu-latest`. Emulated boot is slow but bounded; the job needs no privileges
beyond installing the four packages. The `.deb` under test is the artifact
`debian.yml` just built, which closes the loop between "the package built" and
"the package installs".

## Out of scope

- Audio playback, pairing, and anything needing a real sender or a sound card.
- Testing on real Pi hardware (this reduces how often that is needed; it does
  not replace it).
- armhf, which needs a 32-bit guest and is the one package never yet run.
- Any use of `sudo` on the host, or a persistent VM. Every run is throwaway.

## Acceptance criteria

1. `./testing/vm/vmtest path/to.deb` boots, installs, asserts and tears down on
   skynet, unprivileged, from a cold cache, exiting 0. **Met** — 215 s against
   the published 0.3.0 arm64 package, every assertion passing.
2. A deliberately broken `.deb` makes it exit non-zero with a message naming the
   failed assertion. **Met** — a package with an uninstallable dependency exits
   1 with apt's "unmet dependencies" output and the path to the full log.
3. Total runtime and the boot timeout are both reported. **Met** — ~60 s to ssh,
   ~215 s total; timeouts are explicit and fail with a message rather than
   hanging.
4. Rerunning does not re-download, and leaves no VM or temp file behind. **Met**
   — the base image is cached and checksum-verified; the work directory and the
   VM are removed on every exit path unless `--keep` is given.

## What the first run found

The daemon logs `avahi advertisement disabled` on first install: it starts
inside the same `apt` transaction that is still configuring `avahi-daemon`,
which is a `Recommends`. It recovers on reboot — but a user installing the
package gets a scary log line and an undiscoverable receiver until something
restarts it. The test reboots and then *insists* the advertisement worked, so
the transient case is visible without failing the run.
