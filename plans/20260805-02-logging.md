# Reduce logging: info = startup/problems, wire diagnostics under debug

- **Date:** 2026-08-05
- **Status:** proposed
- **Scope:** this repository only. Bring the receiver's logging in line with
  openairplay1's convention so a receiver left running while music plays stays
  quiet at `info`, while `RUST_LOG=debug` keeps the full protocol trace.

## Background

With the pincode work merged, a running receiver logged a lot at **info** —
every RTSP request head, connection connect/disconnect, `pair-pin-start` and
`pair-setup` steps, SETUP phases, buffered-audio packet counts, session
start/end, "now playing", and artwork — all of which fire *because music is
playing*. On a long stream that fills the log (and the disk). openairplay1 has
the rule: `info` is startup and problems only; per-request lines, packet
counters, and session/track changes belong at `debug`. This plan applies the
same rule to openairplay2.

## Goals

- `info` is reserved for **startup/shutdown and a small set of one-time
  config lines** (receiver identity, pincode on/off, audio device,
  advertisement, shut down) plus errors (already `warn`).
- Every **wire/session/track** diagnostic — request heads, connect/disconnect,
  pairing steps, SETUP, channel packet counts, session start/end, now playing
  (metadata), artwork, player device line — is at **`debug`**.
- No behavior change: message text, ordering, and debug-level output are
  preserved; only the `info`/`debug` classification and the `log` imports
  change.

## Design

The exact reclassification:

**Keep at `info` (startup / one-time / shutdown):**
- receiver starting (name, deviceid, port, pk), pincode required/off,
  audio output device, Avahi advertisement, "shutting down".

**Move to `debug` (wire/session/track):**
- `[peer] connected` / `disconnected`, and every request head
  (`log_request`: method/target/protocol + headers/body, which are already
  debug).
- `pair-pin-start`, `pair-setup M1`, `pair-setup complete`.
- `SETUP phase 1/2`, the buffered-audio channel line + packet counts, and
  buffered-audio connect/disconnect.
- `session started` / `session ended`, `now playing` (track metadata),
  artwork, and the player's ALSA device line.

This mirrors openairplay1's `notes/protocol.md` + receiver logging convention
(which sources from the same project standards). Files touched: `server.rs`,
`pairing.rs`, `session.rs` (library) and `main.rs`, `player.rs` (receiver),
plus the `use log::{…}` import lines updated where `info` became unused and
`debug` was needed.

## Out of scope

- No behavior, protocol, or dependency changes; no restructuring.
- Not changing the `warn`/`debug` body dumps or the hex-dump of request bodies
  (those stay as-is; relevant to troubleshooting).
- openairplay1 is not touched here.

## Phases

Single implementation phase — this is a contained, mechanical reclassification
(PR #41 on this stack). No plan approval re-opens the design; the plan record
documents scope and the exact mapping.

## Test strategy

- No logic under test changes; the full workspace suite (`cargo test`) and
  `clippy --all-targets -D warnings` must stay green, `fmt` clean.
- Runtime check (acceptance): with `--pincode` set and a sender streaming,
  `info` output is just the startup lines; nothing fires per request or per
  session. `RUST_LOG=debug` still shows request heads, pairing, SETUP,
  packet counts, session start/end, and now-playing.

## Acceptance criteria

- A receiver streaming from a real sender prints **no** per-request, per-packet,
  per-session, or now-playing lines at `info` — only startup/shutdown.
- `RUST_LOG=debug` output is unchanged in substance (same diagnostics, now
  gated at debug).
- `cargo test`, `clippy --all-targets -D warnings`, `cargo fmt --check` green;
  no new dependencies; library still ALSA-free and macOS-green.
