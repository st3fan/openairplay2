# Package openairplay2-tui as a .deb

Roadmap 0.4: the display is the most visible thing in the project, and today
the only way to get it is a Rust toolchain (`cargo build` or `cargo install
--git`). Anyone following "install the `.deb`" gets the daemon and no screen.
This plan ships `openairplay2-tui_X.Y.Z-1_{amd64,arm64,armhf}.deb` from the
same release that ships the receiver's packages.

## Background

The receiver's packaging ([plan](20260805-03-debian-packages.md),
[armhf](20260805-04-armhf-package.md)) established the pipeline: cargo-deb
driven by `[package.metadata.deb]`, `packaging/build-deb.sh` per architecture
(amd64/arm64 native, armhf cross-compiled), `debian.yml` building all three in
`debian:trixie` containers, attesting provenance, and attaching the results to
the release.

The tui is a much simpler package than the receiver, because it is an
interactive terminal program, not a daemon:

- **No systemd unit, no system user, no conffile, no state directory.** You run
  it in a terminal you are sitting at; configuration is its three command-line
  flags (`--connect`, `--images`, `--log-file`).
- **No ALSA.** It depends on neither the library nor the audio stack — it is a
  WebSocket client and a renderer. Its only runtime dependency is `libc6`,
  which also makes the armhf cross-build trivial: the existing toolchain more
  than covers a binary with no native libraries.
- Of the receiver's four maintainer scripts, only the **`preinst` ARMv6 guard**
  applies: an armhf tui on a Pi Zero W would SIGILL exactly like the receiver
  would, and dpkg cannot tell Debian armhf from Raspbian armhf. The
  postinst/postrm user-and-state machinery is daemon-specific and must *not*
  come along.

## Scope

- A `openairplay2-tui` `.deb` for amd64, arm64 and armhf: the binary, the
  README, and the ARMv6 `preinst` guard. Version in lockstep with everything
  else, as always.
- `debian.yml` builds and attaches **six** packages per release (plus
  `SHA256SUMS`, which already covers whatever lands in the dist directory).
- The receiver's package gains `Suggests: openairplay2-tui`. Suggests rather
  than Recommends: the display is an optional companion, and the receiver's
  natural home is a headless box while the display often runs on a different
  machine entirely.
- README install section and the runbook's release-verification step updated
  for the second package.

**Out of scope:**

- Publishing `openairplay2-tui` to crates.io (`cargo install`-ability). Its
  manifest stays `publish = false`; since #74 it is publish-ready if that
  decision ever changes, but a `.deb` is how this plan says "install the
  display".
- macOS distribution (Homebrew or otherwise). The display deliberately runs on
  macOS; macOS users build from source for now. File an issue if this deserves
  to exist.
- The VM install test (`testing/vm`, PRs #69/#70, draft) — it exercises the
  receiver package; extending it to the tui package belongs to that work when
  it lands.
- The apt repository — that is 0.5.

## Design

### Package metadata (`openairplay2-tui/Cargo.toml`)

`[package.metadata.deb]` mirroring the receiver's conventions:

- `name = "openairplay2-tui"`, `section = "sound"`, `priority = "optional"`.
- `depends = "libc6"` — pinned by hand like the receiver's, so all three
  architecture legs produce identical metadata rather than trusting shlibdeps
  per leg. No ALSA, no Avahi, no adduser.
- `extended-description` saying what it is and that it needs a receiver started
  with `--tui-listen`.
- `assets`: the binary to `usr/bin/`, the README to
  `usr/share/doc/openairplay2-tui/`.
- `maintainer-scripts = "../packaging/tui-debian"` — a new directory containing
  **only** a `preinst` with the ARMv6 refusal (message naming
  `openairplay2-tui`). The receiver's `packaging/debian/` stays untouched; the
  two packages must not share maintainer scripts, because the receiver's are
  daemon-specific.
- No `[package.metadata.deb.systemd-units]`.

### Build script (`packaging/build-deb.sh`)

Builds **both** packages for the requested architecture — same invocation, same
native/cross split — and reports both paths. The single `deb=` GitHub output
becomes two (`receiver_deb=`, `tui_deb=`); the "hand the path to the workflow
rather than making it guess with globs" principle stands.

### Workflow (`debian.yml`)

- The attest step's `subject-path` takes both paths (the action accepts
  multiple subjects); each package gets its own provenance.
- The per-arch artifact carries both `.deb`s (artifact renamed
  `debs-${arch}`, since it is no longer only the receiver's).
- The assets job is untouched: it already globs the merged dist directory, so
  `SHA256SUMS` and the release upload cover six files without change.
- The armhf leg's "tests don't run here" caveat already covers the tui — the
  amd64 and arm64 legs run the workspace tests, tui included.

### Docs

- README "Install (Debian / Ubuntu)": the display gets its install line beside
  the receiver's, and the display section stops implying `cargo build` is the
  only way.
- `runbooks/releasing.md` step 5: "all three `.deb`s" becomes all six, and the
  install smoke-check gains the tui.

## Test strategy

- **Local**: `./packaging/build-deb.sh` on skynet (amd64 native), then
  `dpkg-deb --info/--contents` on the tui package — correct name, version,
  `Depends: libc6` only, no unit files, `preinst` present, binary and README at
  the right paths. Same inspection of the receiver package to prove it is
  unchanged apart from `Suggests`.
- **CI without releasing**: run `debian.yml` by hand (workflow_dispatch) — all
  three architectures build, artifacts carry two `.deb`s each, nothing is
  attached anywhere (the existing smoke-test path).
- **Hardware**: install the tui `.deb` on skynet, run `openairplay2-tui
  --connect` against a live receiver, confirm display and cover art — the
  hardware check that is part of every milestone's acceptance.

## Acceptance criteria

- A release attaches `openairplay2-receiver_…` **and** `openairplay2-tui_…` for
  all three architectures, plus a `SHA256SUMS` covering all six, each with a
  verifiable provenance attestation.
- The tui package installs on Debian 13 with no ALSA/Avahi dependencies pulled
  in, and the installed binary connects to a receiver and draws.
- The armhf tui package refuses ARMv6 hardware at preinst, naming itself.
- Installing the receiver package on a machine with the tui package present
  keeps working (no file conflicts, `Suggests` resolves).
- README and runbook describe the two-package reality.
